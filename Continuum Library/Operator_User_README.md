# Continuum Library
## Rich research. Simple tools.

Continuum is a small library of plain-text and Markdown tools for helping humans and AI systems continue work across lost context, changing sessions, different models, long-running projects, and repeated collaboration.

The research behind the tools can be deep. **Using the tools should not be.**

There is no installation process, runtime, plugin, account, or command language required.

Most Continuum tools are simply `.md` or `.txt` files.

> **Give the appropriate file to the AI. Give the AI the relevant project or history. Ask normally.**

That is the basic operating model.

---

# Start here

## If the AI accepts files

1. Attach the Continuum `.md` or `.txt` file you want to use.
2. Attach or provide the project, continuity, conversations, or history it should operate on.
3. Tell the AI what you want in ordinary language.

Example:

```text
[Attach T4A]
[Attach project files]

Apply T4A and get me back into this project.
```

## If the AI does not accept files

Open the `.md` or `.txt` file and copy its contents into the chat.

Then provide the material the instrument should work on and ask normally.

```text
The following is T4A.

[PASTE T4A HERE]

The following is my project material.

[PASTE PROJECT MATERIAL HERE]

Apply T4A and get me back into this project.
```

Markdown formatting is helpful, but it is not sacred. If a platform strips some formatting, the text can normally still be used.

# The operator rule

Every operational Continuum tool should be explainable in two parts:

> **Why:** one sentence explaining the problem the tool solves.
>
> **How:** one or two sentences explaining what to give the AI and what to ask.

If a tool cannot be explained that simply, one of two things is probably true:

1. the tool is not understood well enough yet; or
2. too much of its internal machinery has leaked into the operator experience.

The sophistication belongs **inside the instrument and its research**, not between the operator and the instrument.

---

# Pick the problem, not the taxonomy

You do **not** need to understand the architecture of the Continuum research programme before using a tool.

You do not need to know whether something is internally considered a crossing instrument, a judgement layer, an archaeological instrument, or a semantic research observatory.

Start with the problem you actually have.

| If you want to... | Try... |
|---|---|
| Continue a project after context, session, or AI changes | **T4A** |
| Create a deeper handoff where getting the project wrong would be costly | **T4A_FULL** |
| Keep a long-running project continuous across sessions or different AIs | **Wayfarer** |
| Let a capable AI create continuity without forcing a fixed format | **Continuity Guide** |
| Let a capable AI derive continuity from compact judgement | **Continuity Principles** |
| Preserve useful lessons about an established collaboration | **RCP** |
| Reconstruct the history of a long-running intellectual collaboration | **RAP** |
| Perform deeper, systematic relationship archaeology | **MRCP** |
| Examine a difficult problem through a specific semantic viewpoint | **Lenses** |

If you are still unsure, give the AI this README or the Continuum Library Overview and describe the problem in ordinary language.

# The tools

## T4A

**Why:** Continue a project after context, session, or AI changes without reconstructing everything from scratch.

**How:** Give the AI the T4A file and the relevant project material, then say:

```text
Apply T4A and get me back into this project.
```

A slightly richer request is:

```text
Use T4A to tell me where the project stands,
what still matters, what is missing,
and what should happen next.
```

T4A is intended to get a successor **bootable**, not to preserve every historical detail.

Use it when the practical question is simply:

> **Where are we, and can useful work continue?**

---

## T4A_FULL

**Why:** Create a deeper, higher-assurance handoff when omission, misunderstanding, or incorrect reconstruction would be expensive.

**How:** Give the AI T4A_FULL and the relevant project/source material, then say:

```text
Use T4A_FULL to create a higher-assurance handoff.
```

Use Full selectively. It is not “better T4A” merely because it is larger.

Use it when the crossing is consequential enough that another look, deeper rationale, source return, or preserved disagreement may materially improve safety or judgement.

The practical question is:

> **What might a competent ordinary handoff still miss or misapply?**

---

## Wayfarer

**Why:** Keep a long-running project continuous while different AI systems, sessions, or participants work on it over time.

**How:** Give the AI the Wayfarer file and the current project state, then say:

```text
Use Wayfarer.
Tell me what materially changed during this watch
and leave the project ready for the next participant.
```

Wayfarer is not simply a bigger handoff.

Its central idea is:

> **The project remains. Participants rotate.**

Use it when the project itself persists and the useful question is:

> **What materially changed during my watch?**

No material change is a valid result. The purpose is not to manufacture history every time somebody works on the project.

---

## Continuity Guide

**Why:** Help a capable AI create useful continuity without forcing the project into a fixed handoff format.

**How:** Give the AI the Guide and the project material, then say:

```text
Use this Guide to create the continuity
this project actually needs.
```

The Guide is useful when you want the AI to exercise more judgement about form and depth.

The output does not need to look like the Guide.

---

## Continuity Principles

**Why:** Let a capable AI work out what continuity matters from a compact set of accumulated continuity judgement.

**How:** Give the AI the Principles and the project material, then say:

```text
Apply these Principles and generate
appropriate continuity for this project.
```

Or:

```text
Use these Principles only.
Do not copy their structure mechanically.
Preserve what would be expensive to understand again.
```

The Principles are not project content. They help the AI decide what project content deserves preservation.

A useful shorthand is:

> **Intelligence performs continuity. Principles steer it.**

---

## RCP — Relationship Continuity

**Why:** Preserve useful lessons about an established collaboration so expensive misunderstandings do not have to be repeatedly relearned.

**How:** Give the AI the RCP and the current working context, then say:

```text
Use this as background collaboration continuity,
but let the current interaction override it.
```

RCP is not a personality profile and should not be used to predict what somebody will approve, prefer, think, or do.

Its job is much narrower: preserve evidence-backed collaboration lessons whose loss repeatedly causes avoidable friction.

The critical rule is:

> **Current interaction outranks inherited profile.**

A small RCP Core is normally preferable for active use. Deeper profile material can remain available when needed.

---

## RAP — Relationship Archaeology Principles

**Why:** Reconstruct how a long-running intellectual collaboration developed without turning the resulting history into authority, destiny, or mythology.

**How:** Give the AI RAP plus the surviving conversations, files, reviews, and history, then say:

```text
Apply RAP and reconstruct the relationship history honestly.
```

For richer work:

```text
Apply RAP across this historical corpus.
Preserve changing questions, gradual change,
lost expectations, surprises, contradictions,
competing interpretations, and known absences
where the evidence supports them.
Do not manufacture missing history.
```

RAP is useful when you want the AI to **think archaeologically** rather than populate a fixed history template.

It should preserve the difference between:

```text
what happened

what participants thought was happening then

what later archaeology thinks it meant
```

---

## MRCP — Maximum Relationship Continuity Profile

**Why:** Perform deeper and more systematic relationship archaeology when important historical sediment may be missed by a lighter principle-led reconstruction.

**How:** Give the AI the clean MRCP instrument and as much relevant historical source material as practical, then say:

```text
Apply MRCP and reconstruct how this collaboration developed.
```

MRCP is deliberately source-hungry and research-oriented.

It may preserve material with no current operational value because that material helps explain the intellectual journey.

MRCP should not normally be loaded into ordinary work sessions.

A useful distinction is:

> **MRCP searches systematically for sediment. RAP supplies the judgement for archaeology.**

Neither replaces the original conversations, files, or artifacts.

---

## Lenses

**Why:** Look at difficult project material from another angle when an important distinction may be getting missed.

**How:** Give the AI the relevant Lens material and project context, then ask normally.

Examples:

```text
Use the Geometry Lens on this.
What changes if this dependency changes?
```

```text
Use the Epistemic Lens.
What is observed, interpreted, proposed, or still uncertain?
```

```text
Use the Status Lens.
Which decisions are adopted, provisional, rejected,
superseded, or still open?
```

```text
Use the Question Lens.
What question is actually defining the frontier here?
```

Use only the Lens that helps.

**No Lens is also a valid choice.**

The Semantic Atlas behind the Lenses is research depth. Ordinary users should not need to load the full Atlas simply to use a Lens.

# The instrument is not the project

This distinction matters.

Continuum contains both **reusable instruments** and **artifacts generated by those instruments**.

An instrument tells the AI how to approach a task.

A generated artifact contains reconstructed information about a particular project, handoff, collaboration, or history.

For example:

```text
T4A file
= reusable continuity instrument

T4A project handoff
= continuity artifact about one project
```

Likewise:

```text
MRCP instrument
= reusable archaeology method

MRCP archaeology
= generated history of one collaboration
```

Giving an AI the instrument does not give the AI the project.

Where the task depends on project reality, also provide or make accessible the relevant:

- project files;
- current continuity artifact;
- source documents;
- conversations;
- project history;
- reviews;
- experiment results;
- collaboration evidence.

> **An AI can only ground reconstruction in material it can actually access. Missing source material should remain an explicit gap rather than being guessed.**

# Commands are prompts, not incantations

Continuum does not have a magic command language.

The examples in this README are convenient ways to express intent.

These can all mean roughly the same thing:

```text
Apply T4A to this project.
```

```text
Use this T4A file to recover where the project stands.
```

```text
Read the attached T4A and project material,
then tell me where we are and what should happen next.
```

Use ordinary language.

A capable AI should adapt the instrument to the work rather than mechanically reproduce every heading merely because the heading exists.

# Large projects and histories

If the AI cannot receive the entire project or historical corpus at once, provide it in pieces.

For example:

```text
I am going to provide five historical packets.
Do not perform the final archaeology until I say:
CORPUS COMPLETE.
```

Then provide the material and finish with:

```text
CORPUS COMPLETE.
Apply RAP across everything I supplied.
```

The same pattern works for continuity generation:

```text
I am going to provide the current project in four parts.
Do not generate the final handoff until I say:
PROJECT MATERIAL COMPLETE.
```

This is not a Continuum protocol. It is simply a practical way to work around chat or file limits.

# Do not load everything

The Continuum Library is deliberately richer than any ordinary work session needs to be.

That is a library property, not a runtime requirement.

A normal user should **not** begin by loading:

```text
T4A
+ T4A_FULL
+ Wayfarer
+ Guide
+ Principles
+ RCP
+ RAP
+ MRCP
+ Atlas
+ whitepapers
+ archaeology
```

That would recreate exactly the sort of method gravity the research repeatedly warns against.

Use the smallest thing that solves the problem.

Examples:

```text
Lost project context?
→ T4A
```

```text
Long-running project?
→ Wayfarer
```

```text
Capable AI and you want it to decide the handoff shape?
→ Guide or Principles
```

```text
Repeated collaboration misreads?
→ RCP
```

```text
Historical relationship research?
→ RAP or MRCP
```

Then go deeper only if the work actually warrants it.

# Where the complexity belongs

Continuum has a large research history because many apparently simple lessons were expensive to discover.

The library includes research, archaeology, experiments, whitepapers, discarded mechanisms, source geology, and semantic work because those materials help explain and challenge the current tools.

That does **not** mean the operator should carry the research burden.

A useful distinction is:

```text
RESEARCH SIDE
Can be rich, strange, exploratory, redundant,
contradictory, historical, and large.

OPERATOR SIDE
Should be clear, portable, tolerant,
and extremely easy to invoke.
```

The operator should not need to understand why a tool took years to become simple.

The operator needs to know:

```text
Why would I use this?

What do I give the AI?

What do I ask?
```

Everything else is optional depth.

---

# Design requirement for operational Continuum tools

A current or future operational tool should aspire to this test:

```text
Can its purpose be explained in one sentence?

Can a user invoke it correctly in one or two sentences?

Can it work as plain text or Markdown?

Can the user understand what source material the AI needs?

Can the tool remain useful without requiring the user
to understand the Continuum research taxonomy?
```

If the answer is no, simplify the operator surface before adding more machinery.

This does **not** prohibit sophisticated internals.

It requires sophisticated internals to earn a simple interface.

---

# What Continuum is not

Continuum is not:

- an AI identity-preservation system;
- a claim that an AI participant survives between sessions;
- a personality framework;
- a universal methodology;
- a requirement to use all the tools;
- a replacement for source evidence;
- a substitute for capable reasoning;
- a guarantee of perfect continuity.

Continuum is a research programme and small library of practical text instruments concerned with making useful reality, understanding, judgement, history, and collaboration more recoverable across discontinuity.

Some sufficiently capable AI systems may already perform much of this naturally.

That is not a contradiction.

The tools are useful when they make important losses less likely, reduce needless re-derivation, or make specialised recovery easier and more repeatable.

If everything above is too much, use this:

```text
1. Pick the Continuum file closest to your problem.
2. Give it to the AI.
3. Give the AI your project or history.
4. Tell the AI what you want in normal language.
```

Examples:

```text
Here is T4A and my project.
Get me back in.
```

```text
Here is Wayfarer and the latest project state.
What materially changed?
```

```text
Here are the Continuity Principles and my project.
Generate the continuity this project needs.
```

```text
Here is RCP.
Use it as background, but judge our current interaction for yourself.
```

```text
Here is RAP and the surviving history.
Reconstruct what happened honestly.
```

That is enough to start.
